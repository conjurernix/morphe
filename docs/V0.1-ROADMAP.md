# Morphe v0.1 roadmap

Morphe v0.1 supports shipping small and medium 2D desktop games from Clojure. It covers the common LÖVE workflow with
immutable game state and data-driven effects.

Full LÖVE parity is a longer target. The first public release establishes the runtime, graphics, audio, input, files,
packaging, and quality needed by real games.

## Target

The comparison baseline is LÖVE 11.5 and its official modules. Parity means a developer can finish the same common 2D
games. Names and implementation details may differ.

Morphe keeps its existing strengths:

- Game updates remain deterministic and independent from rendering.
- Game state and commands remain plain data where practical.
- Windows, graphics, audio, files, and other effects remain adapter concerns.

Morphe v0.1 does not promise an editor, 3D rendering, networking, mobile, or consoles. LÖVE does not bundle an editor or
networking either.

## LÖVE capability map

| LÖVE area                            | Morphe v0.1 target                                                                                 | Later parity                                                    |
|--------------------------------------|----------------------------------------------------------------------------------------------------|-----------------------------------------------------------------|
| `love`, `event`, `timer`             | Fixed updates, interpolation, quit, pause, focus, resize, error handling                           | Custom loops and advanced timer statistics                      |
| `graphics`, `font`, `image`          | Batched 2D drawing, transforms, cameras, atlases, text, canvases, particles, clipping, blend modes | Meshes, custom shaders, stencil operations, compressed textures |
| `window`, `system`                   | Resizing, fullscreen, VSync, DPI scaling, clipboard, display information                           | Multiple windows and broader platform services                  |
| `keyboard`, `mouse`, `joystick`      | Complete keyboard events, text input, mouse, wheel, gamepads, remapping                            | Haptics and uncommon joystick controls                          |
| `audio`, `sound`                     | Static sounds, streamed music, pause, seek, loop, volume groups, pitch                             | Positional audio, recording, and advanced effects               |
| `filesystem`, `data`                 | Packaged resources, per-game save directory, EDN and byte access, atomic writes                    | Compression, hashes, encodings, and archive mounting            |
| `math`                               | Vectors, transforms, interpolation, collision shapes, deterministic random input                   | Triangulation, Bezier utilities, and noise families             |
| `physics`                            | AABB queries, spatial indexing, ray casts, and tile collisions                                     | A supported Box2D adapter matching `love.physics` workflows     |
| `thread`, `video`, `touch`, `sensor` | Outside the v0.1 contract                                                                          | Required before claiming broad LÖVE parity                      |

## Required before v0.1.0

### 1. Runtime and application lifecycle

| Requirement                                      | State    | Acceptance                                                                             |
|--------------------------------------------------|----------|----------------------------------------------------------------------------------------|
| Entity lifecycle, context, scenes, and snapshots | Done     | Runtime contract tests cover ordering, restoration, and malformed input                |
| Fixed timestep                                   | Done     | Updates run at a configured rate with bounded catch-up and render interpolation        |
| Application control                              | Done     | Games handle quit, pause, focus, resize, and fatal errors through documented callbacks |
| Replay support                                   | Done     | Recorded input and random values reproduce the same final snapshot                     |

See the [v0.1 runtime contracts](V0.1-RUNTIME-PLAN.md) for the public API, behavior, and validation coverage.

The fixed loop owns an accumulator. It must never pass an unbounded wall-clock delta into game logic. Rendering may run
faster or slower than updates.

### 2. Production 2D adapter

| Requirement          | State    | Acceptance                                                                                                       |
|----------------------|----------|------------------------------------------------------------------------------------------------------------------|
| Modern renderer      | Done        | Buffered drawing replaces immediate-mode OpenGL and batches compatible commands                                  |
| 2D graphics          | Done        | Sprites, atlas regions, shapes, lines, polygons, transforms, cameras, text, clipping, and canvases work together |
| Asset manager        | Done        | Classpath and packaged resources load once, report failures, and release native memory                           |
| Audio                | Done        | Short sounds and streamed music support volume, pause, loop, seek, groups, and clean shutdown                    |
| Input and windows    | Done        | Keyboard, text, mouse, wheel, gamepad, resize, fullscreen, VSync, DPI, clipboard, and display data use stable shapes |
| Collision foundation | Done     | Spatial queries avoid checking every entity pair and support platformer and top-down maps                        |

`examples/platformer-lwjgl/src/platformer/assets.clj` remains a generated-art fixture. The public asset API must load
game resources from JARs and packaged applications.

Quil remains an educational adapter unless it passes the same contracts. LWJGL is the production desktop adapter.

### 3. Public distribution

| Requirement         | State    | Acceptance                                                                                                              |
|---------------------|----------|-------------------------------------------------------------------------------------------------------------------------|
| Supported platforms | Required | Packaged games run on Windows x64, Linux x64, and macOS x64 and arm64                                                   |
| Release artifacts   | Required | Core and LWJGL artifacts install from Clojars without local roots                                                       |
| Game packaging      | Required | One documented command builds a runnable application with code, assets, natives, and metadata                           |
| Public API policy   | Required | Public namespaces, errors, deprecations, and compatibility rules are documented                                         |
| Documentation       | Required | Quickstart, API reference, concepts, asset guide, packaging guide, and troubleshooting are tested from a clean checkout |
| Release identity    | Required | README, changelog, build defaults, tags, coordinates, and repository URLs agree on v0.1.0                               |

## Release validation

### Game validation

Each game must build from published artifacts and run without repository-local dependencies.

| Game                 | Proves                                                                                               |
|----------------------|------------------------------------------------------------------------------------------------------|
| Platformer           | Dynamic entities, collision, cameras, animation, particles, audio, gamepad input, and scene changes  |
| Top-down action demo | Tilemaps, atlases, spatial queries, many moving objects, music, pause, and save/load                 |
| Puzzle or card game  | Fonts, mouse and text input, UI scaling, resizing, clipping, persistence, and accessibility controls |

### Performance validation

Use a named reference machine with a four-core x64 CPU, integrated graphics, and 8 GiB RAM. Publish raw results with
each release candidate.

| Gate        | Pass condition                                                                                            |
|-------------|-----------------------------------------------------------------------------------------------------------|
| Frame time  | Each validation game sustains 60 FPS at 1080p, with p99 frame time at or below 16.67 ms                   |
| Simulation  | The existing 10,000-targeted-event workload stays below 4 ms median and regresses by no more than 5%      |
| Rendering   | Ten thousand visible sprites batch into at most 100 draw calls without per-frame native allocation growth |
| Stability   | A 30-minute automated run has bounded memory and no uncaught exceptions or native resource leaks          |
| Determinism | Runs rendered at 30, 60, and 144 FPS produce the same snapshot after equal fixed updates                  |

### Platform and release validation

| Gate             | Pass condition                                                                                                            |
|------------------|---------------------------------------------------------------------------------------------------------------------------|
| CI matrix        | Lint, tests, packaging, and smoke tests pass on every supported operating system and architecture                         |
| Clean install    | A temporary project resolves published coordinates, loads packaged assets, opens a window, plays audio, and exits cleanly |
| Distribution     | Every validation game launches from its packaged form without Clojure CLI or a source checkout                            |
| Failure behavior | Missing assets, invalid render commands, audio failures, and unavailable devices return actionable structured errors      |
| Release record   | Changelog, migration notes, checksums, licenses, known limits, and performance results ship with the release              |

## Delivery order

1. **v0.1 alpha:** fixed loop, application events, input model, resource loading, and renderer batching.
2. **v0.1 beta:** graphics breadth, fonts, audio, collision queries, save storage, and three validation games.
3. **v0.1 release candidate:** platform packaging, CI matrix, performance gates, documentation, and public API freeze.

## LÖVE parity after v0.1

Broad parity requires three additional tracks:

- Add a Box2D adapter, worker threads with message channels, and safe background asset decoding.
- Add video, touch, sensors, advanced graphics, and the remaining data and math utilities.
- Maintain a capability test matrix against LÖVE examples and publish explicit compatibility gaps.

Do not claim full LÖVE parity until these tracks pass cross-platform validation.
